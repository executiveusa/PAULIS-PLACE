01 — HERMES ORCHESTRATOR

Repo: pauli-hermes-agent
Runtime: Long-running Node/Python process on VPS 31.220.58.212, systemd-managed
Reads from: event bus (Redis Streams), PAULIS-PLACE DB, Open Brain, YAPPYVERSE-FACTORY character registry
Writes to: icm/memory/ops/, event bus (outbound events), model gateway (delegation)
Reader model: GLM 5.2 (text-only)

1. Purpose in one paragraph

Hermes is the god agent. Hermes does not write code, does not implement, does not touch files inside repo trees other than icm/memory/ops/. Hermes receives events, decomposes them into work items, delegates each work item to the cheapest worker profile that can succeed, then submits every worker output to an adversarial judge before that output is allowed to affect the world. Hermes replaces the human-in-the-terminal for the boring stuff and calls the human when the blast radius exceeds three services or the cost exceeds $10 for a single task.

2. The four things Hermes owns

3. The event bus contract

Hermes speaks to the rest of the system exclusively through the event bus. The bus is Redis Streams (already provisioned for Celery in PAULIS-PLACE). Every event has this shape:

{
  "id": "<ulid>",
  "type": "<domain>.<action>",       # e.g. "revenue.new_trend", "council.debate_request"
  "occurred_at": "<ISO 8601 UTC>",
  "source": "<repo-name>/<module>",
  "correlation_id": "<ulid or null>", # links related events across the chain
  "blast_radius": <integer 1..N>,     # count of services this event will touch downstream
  "cost_estimate_usd": <float>,        # predicted AI cost of processing this event
  "payload": { ... }                    # event-specific, schema in icm/context/ENVELOPES.md
}
Hermes rejects any event with blast_radius > 3 unless it carries a signed multi-service plan. The signature is an HMAC over the plan document keyed by a secret only Hermes holds. If unsigned, Hermes emits ops.plan_required and halts the pipeline for that correlation_id until a human signs off.

4. The task profile system (auto-model-switcher)

Hermes never says "use GLM 5.2." Hermes says "this is a write_long task." The gateway picks the model per the profile table, and can be re-tuned without touching Hermes.

Task profile schema (icm/context/TASK_PROFILES.md)
profile_id:            string, one of: plan | judge | implement | write_short | write_long | score | test | docs
max_tokens_out:        integer
requires_reasoning:    boolean            # if true, gateway must pick a reasoning-tier model
requires_vision:       boolean            # if true, GLM 5.2 is excluded
max_cost_usd:          float              # gateway rejects the call if predicted cost exceeds this
preferred_provider:    string or null     # optional pin, e.g. "openrouter" or "anthropic"
timeout_seconds:       integer
retry_policy:          {max_retries, backoff_seconds}

Every worker call from Hermes to the gateway is a five-field message: {profile_id, system_prompt_path, user_prompt_path, expected_envelope_type, correlation_id}. The gateway resolves the profile to a concrete model and provider at call time.

5. The delegate → judge → emit loop

STEP 01.5.1
Receive event from bus
Hermes subscribes to the hermes.inbox Redis stream. Every message triggers the loop. If the stream backlog exceeds 1000 messages, Hermes emits ops.backlog_high and starts shedding lowest-priority events (docs, score, write_short profiles first) until the backlog is below 500.
STEP 01.5.2
Load context deterministically
Hermes reads three files, in this order: icm/instructions/HERMES.md, icm/context/EVENT_BUS.md, and the event-type-specific handler at icm/instructions/HANDLERS/<event_type>.md. If the handler file is missing, Hermes emits ops.handler_missing and halts.
STEP 01.5.3
Plan — produce a work-item list
Hermes calls the gateway with profile plan, expected envelope PlanEnvelope. The output is a list of work items, each with: work_id, profile_id, worker_prompt_path, expected_envelope, predicted_cost_usd, dependencies. Predicted total cost must be under the event's cost_estimate_usd ceiling, otherwise the plan is rejected and re-prompted with correction "reduce cost."
STEP 01.5.4
Delegate — dispatch work items in parallel groups
Hermes groups work items by their dependencies field (topological sort). Group 1 items with no dependencies run in parallel. Group 2 items depend only on Group 1. Group N depends only on groups 1..N-1. Each worker runs in its own gateway session. Hermes stores the session ids for correction (STEP 01.5.7).
STEP 01.5.5
Judge — every worker output goes to a judge on a different model
For each returned envelope, Hermes calls the gateway with profile judge, providing the worker's output, the original task prompt, and the acceptance criteria for the envelope type. The judge returns {accepted: bool, violations: string[]}. If accepted: false, go to STEP 01.5.7.
STEP 01.5.6
Emit — publish downstream events on acceptance
On acceptance, Hermes writes the envelope to icm/memory/ops/<date>/<correlation_id>/<work_id>.json and publishes zero or more downstream events per the handler's emission map. Emissions carry the same correlation_id so the whole chain is traceable.
STEP 01.5.7
Correction, not restart
On judge rejection, Hermes calls the gateway again in the same worker session (session id from STEP 01.5.4) with the correction message: "You produced X. The judge found these violations: [...]. Produce a corrected envelope of the same type." Retry limit is 3. On 4th failure, emit ops.correction_exhausted and halt. Never restart the worker from a cold session — that discards accumulated context and burns tokens.
STEP 01.5.8
Cost accounting
Every gateway call increments a Redis counter keyed on the current UTC date. If daily total exceeds $5, Hermes stops accepting new events (except system.override events signed by the human). All in-flight work items are allowed to complete.

6. The judge is never the same model as the worker

The adversarial check has no value if the judge shares the worker's blind spots. The gateway enforces this by looking up the worker's actual model (post-profile-resolution) and excluding it from the judge pool. If only one model is available for the judge profile and it matches the worker's model, Hermes emits ops.judge_conflict and halts. Fix by adding a fallback model to the judge pool.

7. Human-in-the-loop gates

Hermes escalates to human review under any of these conditions (encoded in icm/instructions/ESCALATION.md):

  1. Blast radius > 3 services (see section 3)
  2. Predicted cost for a single event > $10
  3. Judge rejected the same worker output 3 times
  4. A worker requested a tool not on its allowed list
  5. A Zernio post targets a platform not on the pre-approved list
  6. A Council ruling touches financial commitments > $100

Escalation channel is one line in a Slack-compatible channel (Zernio can post the same message to Slack, so Hermes emits zernio.post_internal). Human replies "approve" or "deny" — Hermes checks for that keyword in the reply thread every 30 seconds.

9. Boundaries — what Hermes never does

  • Never writes code files. Ever. Not even test files.
  • Never commits to git. Ever.
  • Never touches secrets. Reads them from the vault via SDK, passes them as opaque tokens to the gateway.
  • Never deploys. Deploy is Agent Zero's authority (per EMERALD_TABLETS.md).
  • Never runs a Council debate itself — it dispatches the debate to subsystem 02.
  • Never makes a Zernio post itself — it dispatches to subsystem 05.
  • Never makes a payment decision — it dispatches to subsystem 06.

10. Acceptance criteria (the judge for this subsystem)

When a worker delivers Hermes' implementation, the judge validates:

  1. The event bus contract in section 3 is honored byte-for-byte.
  2. All 8 steps in section 5 are implemented as named functions with matching names.
  3. The auto-model-switcher never resolves a model directly — always through the profile system in section 4.
  4. The judge-vs-worker model-exclusion in section 6 is enforced with a test that would fail if bypassed.
  5. Every disk write listed in section 8 is present and produces the specified JSON shape.
  6. The 6 escalation triggers in section 7 are all implemented; a test exists for each.
  7. Boundary #1 in section 9 is enforced by a lint that scans the codebase for calls that would write to any path outside icm/memory/ops/.
