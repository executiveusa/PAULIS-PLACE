06 — PAYMENTS AND LEDGER

Repo: PAULIS-PLACE, module backend/services/payment_service.py (exists), plus new ledger_service.py
Reader model: GLM 5.2 (text-only)

1. Purpose

Two gateways: Creem for USD cards, BTCPay for Bitcoin and Lightning. No other gateways. Every settled payment triggers a chain: (a) grant access to the paid artifact, (b) append a row to the internal ledger, (c) dispatch a scene event to the 3D world so Pauli rings the bell, (d) if the total daily settled revenue crosses a threshold, dispatch a Zernio celebration post (Publisher character). Reconciliation runs hourly.

2. Webhook contracts

GatewayWebhook URLSignature headerEvent we care about
CreemPOST /webhooks/creemX-Creem-Signature HMAC-SHA256checkout.settled
BTCPayPOST /webhooks/btcpayBTCPay-Sig HMAC-SHA256InvoiceSettled
Both webhooks MUST verify the signature before doing anything with the payload. Unsigned or invalid-signature requests are logged to icm/memory/ops/<date>/webhook_rejected.jsonl and return 200 OK (never leak the rejection reason to a bad actor). A run of 10+ invalid signatures in an hour trips a circuit breaker and emits ops.webhook_attack_suspected.

3. The event chain per settlement

  1. Webhook arrives → signature verified → payload extracted.
  2. Idempotency check: has this invoice_id already been processed? Redis SETNX with 24h TTL. If already processed, return 200 OK and stop.
  3. Emit payment.settled to the bus with {gateway, invoice_id, amount_usd, currency, product_id, buyer_email or null, correlation_id}.
  4. Access grant worker (subsystem 03 role) receives the event and marks the buyer's access rights in the product access table.
  5. Ledger append worker writes a row to backend/db/ledger.
  6. Scene event lounge.payment_celebration fires — Pauli rings the bar bell twice (subsystem 07).
  7. Daily threshold check: if today's total crossed a threshold (default $100, $500, $1000), dispatch a Zernio celebration post via subsystem 05.

4. The ledger schema (Postgres)

CREATE TABLE ledger_entries (
  id                bigserial PRIMARY KEY,
  occurred_at       timestamptz NOT NULL,
  gateway           text NOT NULL,               -- 'creem' | 'btcpay'
  invoice_id        text NOT NULL UNIQUE,        -- prevents double-writes
  product_id        text NOT NULL,
  amount_usd        numeric(12,2) NOT NULL,
  currency_original text NOT NULL,               -- e.g. 'USD', 'BTC'
  amount_original   numeric(24,8) NOT NULL,
  fx_rate           numeric(18,8),               -- USD per unit of original currency
  buyer_hash        text,                        -- SHA-256 of buyer email, never the email itself
  correlation_id    text NOT NULL,
  payload_json      jsonb NOT NULL,              -- full webhook payload for audit
  created_at        timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ledger_occurred_at_idx ON ledger_entries (occurred_at DESC);
CREATE INDEX ledger_product_idx     ON ledger_entries (product_id);

5. Reconciliation loop (hourly)

Cron on the hour. For each gateway, list settled invoices in the last 2 hours and cross-check against the ledger. Any settled invoice not in the ledger triggers ops.reconciliation_gap and is retried through the event chain (with idempotency, so it self-heals).

6. Refunds

Refund handling is human-gated. A refund event does not automatically revoke access — it emits ops.refund_pending and waits for the human's voice command in the lounge ("Revoke access for order X") before revoking.

7. Acceptance criteria

  1. Both webhook signatures are verified with real HMAC checks; a unit test with a known-bad signature returns 200 OK but does not process.
  2. Idempotency prevents double-processing under a concurrent duplicate webhook (test with two identical POSTs).
  3. Ledger schema exists and every field is populated.
  4. Reconciliation gap self-heals within one hour under a simulated missed webhook.
  5. Refunds do not automatically revoke; a lounge command is required.
