02 — ADVERSARIAL COUNCIL

Repo: PAULIS-PLACE — adds to adws/adw_council_debate.py
Dispatched by: Hermes (subsystem 01) when a council.debate_request event arrives
Reader model: GLM 5.2 (text-only)

1. Purpose

Every non-trivial decision in Paulie's Place goes through the Council — a three-turn structured debate that produces a locked ruling. This is the adversarial-check discipline from the Tracer transcript, applied to business decisions rather than code review. The Advocate argues for the action. The Critic tears the argument down. The Judge synthesizes and rules. The Judge is on a different model than the Advocate and Critic — never let one model referee its own reasoning.

3. The envelope schema

CouncilRulingEnvelope:
  correlation_id:      string
  topic:               string                       # what was being debated
  advocate_argument:   string, min 200 chars
  critic_argument:     string, min 200 chars
  judge_ruling:        enum ("proceed" | "reject" | "revise")
  judge_reasoning:     string, min 100 chars
  final_brief:         string or null               # populated only if proceed
  next_action:         string or null               # populated only if revise
  alternative:         string or null               # populated only if reject
  confidence:          float 0..1
  time_to_first_dollar_days:  integer or null
  estimated_roi_30d:   float or null

4. The four hard rules

  1. Judge cannot be the same model as advocate or critic. Enforced by the gateway (subsystem 01 section 6). If the pool cannot provide a distinct judge model, halt.
  2. Judge does not start with "proceed" unless the advocate survived the critic's attack. Encoded in the judge's system prompt at icm/instructions/COUNCIL_JUDGE.md as an assertion the judge must reason about explicitly before answering.
  3. Reject requires an alternative. A judge that rejects without naming a better opportunity is emitting an unusable envelope — Hermes returns it as a violation.
  4. Time-to-first-dollar must be under 14 days OR the ruling is revise, not proceed. Long-payoff bets are legitimate but they are not proceed-eligible without an explicit human override.

5. The debate flow — 6 steps

STEP 02.5.1
Hermes emits council.debate_request
Payload includes: topic, context_document_path, correlation_id, max_total_cost_usd (default $0.25).
STEP 02.5.2
Advocate turn
Worker loads icm/instructions/COUNCIL_ADVOCATE.md, produces an AdvocateEnvelope. If min-char count fails, Hermes corrects in-session.
STEP 02.5.3
Critic turn
Worker loads icm/instructions/COUNCIL_CRITIC.md plus the advocate's envelope. Produces a CriticEnvelope. Must reference at least 2 specific numbers from the advocate's argument and offer counter-numbers.
STEP 02.5.4
Judge turn
Worker loads icm/instructions/COUNCIL_JUDGE.md plus both envelopes. Produces the CouncilRulingEnvelope from section 3.
STEP 02.5.5
Meta-judge check
A second judge (different model again) validates that rules 1–4 in section 4 were honored. If not, the ruling is voided and STEP 02.5.4 re-runs with the meta-judge's feedback appended as correction. Max 2 attempts before human escalation.
STEP 02.5.6
Emit downstream
On proceed: emit revenue.brief_locked with the final_brief payload. On revise: emit council.revision_requested. On reject: emit council.rejected_with_alternative.

7. Acceptance criteria (judge for this subsystem)

  1. All three roles are implemented and each has its own icm/instructions/ markdown file.
  2. Envelope schema in section 3 is validated with Pydantic (or Zod on the frontend side) at every boundary.
  3. The meta-judge in STEP 02.5.5 is a real second call, on a third model, not a self-check.
  4. The four hard rules in section 4 each have a unit test that would fail if the rule were bypassed.
  5. Emitting downstream events matches the exact type strings in STEP 02.5.6.
