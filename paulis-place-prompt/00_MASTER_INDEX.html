1. What we are building, in one paragraph

The Yappyverse is a living world of AI avatars, backed by real humans, hosted at Paulie's Place — a Seattle-2056 jazz-lounge parody of a mob hangout where the avatars work, argue, and make real business decisions. Every avatar is the face of a real agent role inside PAULIS-PLACE (the revenue factory). Every agent decision is a scene in the world. Every scene is observable by the public in a 3D lounge on the lovable-ai-dreamweaver frontend, controlled by voice like Jarvis. Every revenue event auto-posts to social via Zernio. Everything the humans behind the avatars do gets a "Humans in the Loop" comedy cutaway at the end of the clip. The whole thing runs autonomously, orchestrated by Hermes — the god agent.

3. Hermes — the god agent

Hermes is the runtime orchestrator. Not a dev-time IDE (Orca/Tracer are dev tools — Hermes takes their lessons but runs in production). Hermes lives at pauli-hermes-agent and its job is:

  • Plan — decompose incoming events into typed work items
  • Delegate — route each work item to the cheapest worker that can succeed at it (auto-model-switcher, section 8)
  • Judge — every worker output goes through an adversarial checker before it is accepted (Tracer's "Fable reviews cheap workers" lesson, applied to production)
  • Emit — every accepted output produces a downstream event (Zernio post, agent scene in the 3D world, ops report)

Hermes does not write code. Hermes does not implement. Hermes reads, thinks, splits, delegates, and judges — the exact discipline the Tracer transcript names.

7. The ICM folder method — the repository shape

Every repo uses the same three-folder root, called icm/. This is what makes the whole system model-agnostic and portable — Hermes, GLM, Claude, Kimi, and any future model all read the same files from the same locations.

<repo-root>/
├── icm/
│   ├── instructions/       # WHAT to do — system prompts, role definitions, laws
│   │   ├── HERMES.md
│   │   ├── COUNCIL.md
│   │   ├── SCANNER.md
│   │   ├── SCORER.md
│   │   ├── DESIGNER.md
│   │   ├── PUBLISHER.md
│   │   └── AVATAR_<name>.md
│   ├── context/            # WHERE — repo maps, API contracts, envelope types, current state
│   │   ├── REPO_MAP.md
│   │   ├── EVENT_BUS.md
│   │   ├── ENVELOPES.md
│   │   ├── CHARACTER_REGISTRY.md
│   │   └── OPEN_BRAIN_SCHEMA.md
│   └── memory/             # HISTORY — ops reports, decisions, learned patterns
│       ├── ops/            # dated per-run reports
│       ├── decisions/      # Council rulings, one file per ruling
│       └── patterns/       # promoted lessons the system has learned
└── ... (rest of the repo)
Rationale: the model-agnostic switcher (section 8) can hand any of these files to any model, cheap or expensive, because instructions never assume vision, code capabilities, or model-specific tool syntax. Every file is markdown, every reference is a path, every contract is a JSON schema in context/.

9. What GLM 5.2 workers must know before reading anything else

GLM 5.2 has no vision. Every handoff to GLM is text-only. Rules that must be honored by any spec author writing for GLM:
  • Never write "see the screenshot" or "as shown in the image."
  • Every UI layout is described in words: element name, position (parent + row/column index + top-to-bottom), size intent, semantic role.
  • Every reference is a path or a URL, never a picture.
  • Every code block is complete — no "..." elisions. GLM will not guess.
  • Every ambiguous term is defined inline the first time it appears in the spec.
  • Every step has a numbered position in its subsystem. The judge validates work by step number.
