05 — ZERNIO SOCIAL POSTING

Repo: PAULIS-PLACE — new module backend/services/zernio_service.py, wired into revenue_tasks.py
Dispatched by: Hermes on any revenue.product_created, revenue.channel_output_ready, lounge.humans_in_the_loop_clip_ready event
Reader model: GLM 5.2 (text-only)

1. Purpose

Zernio is the outbound social-posting rail for the whole Yappyverse. Every revenue event that has a shareable artifact — a product listing, a Council ruling clip, a Humans-in-the-Loop segment, an ebook cover — gets auto-posted to the relevant subset of Zernio's 15+ platforms. Every avatar has its own posting persona bound to specific accountIds. Zernio owns the schedule, retries, and platform-specific formatting. Hermes owns whether to post at all.

2. Zernio, in one paragraph, for the reader who has never seen it

Zernio is a REST API at https://zernio.com/api/v1 that publishes and schedules posts to Instagram, TikTok, YouTube, LinkedIn, X, Threads, Reddit, Pinterest, Bluesky, WhatsApp, Facebook, Google Business, Telegram, Snapchat, Discord (15+ platforms). Auth is a bearer key (ZERNIO_API_KEY) obtained through a device-authorization flow at https://zernio.com/auth.md. The Node SDK is @zernio/node; the Python SDK is zernio-sdk. Every post targets one or more connected accounts — each has an accountId discoverable through accounts.list(). A post has content, an array of {platform, accountId}, and optionally a scheduledFor ISO-8601 timestamp. The response wraps the created post under data.post with a Mongo-style _id. All of these SDK method names and field names are exact — do not paraphrase them.

3. The auth flow — do this once

STEP 05.3.1
Check for existing key
Before initiating auth, check ZERNIO_API_KEY in env and in .env. If present, skip to section 4. Do not mint a second key.
STEP 05.3.2
Initiate device auth
POST to https://zernio.com/api/auth/cli/initiate with JSON body {"deviceName": "PAULIS-PLACE Setup"}. Response fields: deviceCode, userCode, browserUrl, expiresAt, interval. Keep deviceCode secret — it is the polling credential.
STEP 05.3.3
Human authorizes in browser
Show the browserUrl to the human. They open it, sign in or sign up, click Authorize. This is the only manual step in the whole system's posting setup.
STEP 05.3.4
Poll until authorized
GET https://zernio.com/api/auth/cli/poll with Authorization: Bearer <deviceCode>. Must be GET, not POST — POST returns 405. Poll interval is interval seconds, minimum 5. Status transitions: pending → authorized (with apiKey field, returned exactly once) → subsequent polls return authorized with no key. On 410, session expired, restart from STEP 05.3.2.
STEP 05.3.5
Persist the key immediately, before anything else
The moment the poll returns {"status":"authorized","apiKey":"sk_..."}, write it to .env: 
ZERNIO_API_KEY=sk_...
Confirm .env is in .gitignore. Never print the key. Never commit it. If you poll again before persisting, the key is gone forever — restart from STEP 05.3.2.

4. SDK initialization

The SDK names, method names, and request field names are exact and must not be paraphrased. Node: @zernio/node, method posts.createPost, args nested under body, response nested under data.post._id. Python: zernio-sdk, method posts.create, snake_case kwargs, response nested under result["post"]["_id"]. The REST field is content, not text. Do not guess variants.

PAULIS-PLACE is Python. Use zernio-sdk. Initialize once at import time:

from zernio import Zernio
client = Zernio()  # reads ZERNIO_API_KEY from env

5. The account discovery workflow — do this at boot and cache

STEP 05.5.1
List accounts on service boot
Call client.accounts.list(). Iterate the returned accounts. Build a lookup: {platform: [accountId, ...]}. Persist to Redis under key zernio:accounts:v1, TTL 1 hour.
STEP 05.5.2
Map accounts to Yappyverse personas
The character-to-account mapping lives in icm/context/ZERNIO_PERSONAS.md. Format: 
| character | platform  | accountId | posting_voice_prompt_path |
| pauli     | instagram | acc_xxx   | icm/instructions/VOICE_PAULI.md |
| pauli     | tiktok    | acc_yyy   | icm/instructions/VOICE_PAULI.md |
| bambu     | linkedin  | acc_zzz   | icm/instructions/VOICE_BAMBU.md |
If a persona references an accountId not in the discovery cache, log a warning and skip that platform for that persona — do not error out the whole run.

6. The post-creation pipeline — one revenue event → many social posts

STEP 05.6.1
Hermes emits an outbound event
Example event types that trigger this subsystem: revenue.product_created, revenue.channel_output_ready, lounge.humans_in_the_loop_clip_ready, council.ruling_clip_ready. Payload includes the artifact and its character context.
STEP 05.6.2
Select target platforms per persona rules
Read icm/context/PLATFORM_MATCH.md. Example rules: sticker products → Pinterest + Instagram + TikTok. Ebook launches → X + Threads + Reddit + Instagram. Humans-in-the-Loop clips → TikTok + YouTube Shorts + Instagram Reels. Micro-app launches → LinkedIn + X + Threads + Reddit.
STEP 05.6.3
Draft post content — dispatch to a worker
For each target platform, Hermes dispatches a write_short profile call with the platform-specific prompt at icm/instructions/POSTING/<platform>.md. Prompt includes the persona voice, the artifact URL, the platform character limit, and the platform-native format cues (hashtags for IG, thread-style for X, hook + payoff for TikTok).
STEP 05.6.4
Judge the draft against the RUTHLESS style law
The judge profile validates: no banned words (delve, tapestry, realm, seamless, robust, innovative, elevate), no em-dashes for emphasis, character length within platform limit, hook exists in first line, product link is intact. Reject → correction loop per Hermes subsystem 01 STEP 01.5.7.
STEP 05.6.5
Schedule or publish via Zernio
Python: 
result = client.posts.create(
    content=drafted_text,
    platforms=[{"platform": "instagram", "accountId": "acc_xxx"}],
    scheduled_for="2026-08-07T18:00:00Z",  # optional
)
post_id = result["post"]["_id"]
Store the returned _id in icm/memory/ops/<date>/<correlation_id>/zernio_posts.jsonl.
STEP 05.6.6
Emit lounge event
Publish lounge.character_posted with {character, platform, post_id, artifact_url}. Subsystem 07 uses this to animate the character in the 3D world holding up a phone showing the post.

8. Scheduling philosophy

Do not publish immediately for most events. Use scheduledFor to spread posts across the target platform's known-good windows (defined per platform in icm/context/PLATFORM_SCHEDULE.md). Immediate publish is reserved for lounge.humans_in_the_loop_clip_ready (time-sensitive comedy) and council.ruling_clip_ready (audience is watching live).

9. Zernio's LLM-readable surface

For endpoint discovery beyond posts (media uploads, inbox, analytics, ads), the machine-readable surface is at https://zernio.com/llms.txt and the OpenAPI is at https://zernio.com/openapi.yaml. Read one of these before adding a new Zernio capability — do not guess endpoint shapes.

10. Acceptance criteria

  1. ZERNIO_API_KEY is present in .env, and .env is in .gitignore. Grep for the key in git history returns nothing.
  2. The 5 event types in STEP 05.6.1 each trigger the pipeline in an integration test.
  3. The RUTHLESS judge (STEP 05.6.4) has a unit test per banned word — a draft containing any of them fails.
  4. The rate limits in section 7 are enforced with Redis counters.
  5. Zernio post IDs are persisted per correlation_id in icm/memory/ops/.
  6. The lounge event in STEP 05.6.6 fires after every successful publish and is received by subsystem 07.
